# Building and releasing

All the application code lives in [`app/`](../app/). Outside it the repository
holds only documentation and screenshots.

## Environment

| Item | Version / place |
|---|---|
| Flutter | 3.47.2 stable (Dart 3.13.2) |
| SDK on the maintainer's machine | `%USERPROFILE%\dev\flutter`, **outside PATH** |
| Android SDK | `%LOCALAPPDATA%\Android\Sdk` |
| Windows | Visual Studio with the "Desktop development with C++" workload, plus developer mode |

Flutter is deliberately kept out of PATH, so the commands below spell out the
full path. If you put it on PATH, plain `flutter` is enough.

Developer mode on Windows (`start ms-settings:developers`) is needed because
the desktop build creates symbolic links to plugins.

**The build needs network access.** `package:sqlite3` version 3 selects its
engine through build hooks and downloads ready-made binaries from GitHub
releases. We ask it there for SQLite3MultipleCiphers
(`hooks.user_defines.sqlite3.source: sqlite3mc` in `pubspec.yaml`); without
that `PRAGMA key` would do nothing and the database would be written in
plaintext. The first build after `flutter clean` downloads them again.

## Day to day

```
cd app
%USERPROFILE%\dev\flutter\bin\flutter.bat pub get
%USERPROFILE%\dev\flutter\bin\flutter.bat run -d windows
```

After a database schema change (`lib/data/db.dart`), the drift code has to be
regenerated:

```
%USERPROFILE%\dev\flutter\bin\flutter.bat pub run build_runner build
```

After changing the strings in `lib/l10n/*.arb`:

```
%USERPROFILE%\dev\flutter\bin\flutter.bat gen-l10n
```

The icons (Android launcher, adaptive icon, notification icon, the `.ico` for
Windows) are generated by a single Python script, which needs Pillow:

```
cd app
python tool/make_icons.py
```

## Build: Windows

```
cd app
%USERPROFILE%\dev\flutter\bin\flutter.bat build windows --release
```

Output: `app\build\windows\x64\runner\Release\`. Moving it to another computer
takes **the whole directory** (the exe plus the DLLs and the `data` directory),
and the target machine needs the "Microsoft Visual C++ Redistributable".

A common error when rebuilding is `LNK1168: cannot open chatt.exe`, which means
the previous instance is still running. Closing the window only **hides the app
in the tray**, so "close it" means "Close Chatt" from the icon menu, or
`Stop-Process -Name chatt`.

### Installer

The installer is built with [Inno Setup 6](https://jrsoftware.org/isdl.php).
The script is in `app\windows\installer\chatt.iss` and the version number comes
from outside, to keep it out of a third place:

```
choco install innosetup -y
"C:\Program Files (x86)\Inno Setup 6\ISCC.exe" /DWersja=0.5.0 app\windows\installer\chatt.iss
```

Output: `dist\chatt-0.5.0-instalator.exe` (the `dist/` directory is in
`.gitignore`). The script takes the **whole** `Release` directory, because the
`.exe` alone, without the libraries and the `data` directory, will not start.
The installation is per user (`PrivilegesRequired=lowest`), so there is no UAC
prompt and the app lands in `%LOCALAPPDATA%\Programs\Chatt`.

The installer is not signed with a certificate, so SmartScreen shows a warning.
Signing requires a paid code-signing certificate; the same would apply to an
MSIX, which is why a plain installer won.

In the release workflow this is the "Instalator" step: Inno Setup is on the
`windows-latest` image, and if it ever disappears the step installs it.

On the first run the Windows firewall asks about incoming traffic. Rules are
created separately for TCP and UDP and separately for the debug and the release
path, so after switching to a release build the firewall asks again. To check
what is allowed through:

```
netsh advfirewall firewall show rule name=chatt verbose
```

## Build: Android

```
cd app
%USERPROFILE%\dev\flutter\bin\flutter.bat build apk --release
```

Output: `app\build\app\outputs\flutter-apk\app-release.apk`.

Installing on a connected device:

```
adb install -r app\build\app\outputs\flutter-apk\app-release.apk
```

### Signing

The release build is signed with our own key. Two files, both **outside git**:

| File | Where | What is inside |
|---|---|---|
| `chatt-release.jks` | `%USERPROFILE%\keys\` | the key (RSA 4096, alias `chatt`, valid to 2053) |
| `key.properties` | `app/android/` | the keystore path, the alias and the passwords |

`app/android/.gitignore` excludes `key.properties`, `*.jks` and `*.keystore`,
and the keystore itself lives outside the project directory. That is what the
Flutter documentation advises, so that it cannot accidentally be added to the
repository.

**A backup of both files is mandatory.** Android ties updates to the signature:
once the key is lost, no new version can be released to anyone who already has
the old one installed. All that is left is uninstalling and installing from
scratch, losing conversations and pairings.

To check what a built APK is really signed with:

```
set JAVA_HOME=C:\Program Files\Android\Android Studio\jbr
%LOCALAPPDATA%\Android\Sdk\build-tools\37.0.0\apksigner.bat verify --print-certs app\build\app\outputs\flutter-apk\app-release.apk
```

It should print `CN=Chatt, O=Mysttic, C=PL` and "Verifies". The signature uses
scheme v2; v1 (JAR signing) is off, because `minSdk` is 24 and v1 is about
older systems.

When `key.properties` or the keystore is missing (a fresh clone, CI without
the secrets), the release build **still passes**, only signed with the debug key,
and Gradle prints a warning. Such an APK is fine for testing but not for
handing out.

**Changing the key in an already installed app**: the first install of an APK
signed with a new key onto a device holding a debug build ends in
`INSTALL_FAILED_UPDATE_INCOMPATIBLE`. The old version has to be uninstalled
once (`adb uninstall com.mysttic.chatt`), which deletes its data.

The manifest permissions and what they are for:

| Permission | What for |
|---|---|
| `INTERNET`, `ACCESS_NETWORK_STATE` | the HTTP server and client on the local network |
| `ACCESS_WIFI_STATE`, `CHANGE_WIFI_MULTICAST_STATE` | MulticastLock, without which the Wi-Fi stack filters broadcasts out and discovery dies |
| `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_CONNECTED_DEVICE` | listening with the window closed |
| `POST_NOTIFICATIONS` | message notifications |
| `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` | the exemption request, called only from settings |

## Version number

The release number lives in [`VERSION.md`](../VERSION.md) at the root of the
repository. **It** decides whether a new release happens: the release workflow
only starts when that file was part of the merged changes.

The second place with the number is `app/pubspec.yaml`, the line
`version: 0.1.0+1`. The part before `+` is Android's `versionName`, the part
after `+` is the `versionCode`, which has to grow with every release. Flutter
copies both values into the native projects, so there is nothing to change in
Gradle or in the Windows files.

Both files have to say the same thing, so they are bumped with one command:

```
cd app
python tool/wersja.py 0.5.0
```

The script raises the number in `VERSION.md` and in `pubspec.yaml`, and
increments the build number by one. With no argument it only prints the current
state and complains if the two disagree. The release workflow checks the same
thing and stops with a readable error if somebody raised the number in one
place only.

## Branches and automation on GitHub

Repository: [github.com/Mysttic/Chatt](https://github.com/Mysttic/Chatt).

```
feature/x ──┐
            ├─→ develop ──(pull request)──→ master ──→ release
claude/x  ──┘                   │                │
                                │                └── Windows build + APK,
                                └── tests            tag and Release
```

- **`develop`** is where current work lands. Ordinary pushes **start nothing**,
  so runners are not burned on every commit.
- **A pull request to `master`** runs
  [`.github/workflows/testy.yml`](../.github/workflows/testy.yml): `flutter
  analyze` and the whole test suite. While the PR is open, commits added to it
  go through the tests again. Otherwise a PR could be merged on the strength of
  a run from before the fixes.
- **A merge into `master`** runs
  [`.github/workflows/wydanie.yml`](../.github/workflows/wydanie.yml): the
  Windows build and a signed APK, a tag and a GitHub Release.

The tests run for every PR **into `master`**, not only from `develop`.
Narrowing it to one source branch would mean a PR from a hotfix branch gets no
check at all, and with green tests required for merging it would hang forever,
waiting for a run that never starts.

The tests can also be started by hand: *Actions, Testy, Run workflow*.

### When a release happens

Two gates, one after the other:

1. **The workflow does not start at all** if [`VERSION.md`](../VERSION.md) was
   not among the merged changes (the `paths` filter on the trigger). Merging a
   code or documentation fix therefore costs no runner time.
2. **The run ends without doing anything** if the `v<version>` tag already
   exists. That is insurance for the case where somebody touched only the
   description in `VERSION.md` without changing the number.

When both gates let it through: the Windows build and a signed APK, a tag and a
Release with three files, `chatt-<version>-android.apk`,
`chatt-<version>-windows.zip` and `chatt-<version>-windows-instalator.exe`.

In practice a release looks like this: `python tool/wersja.py 0.5.0` on
`develop`, a PR to `master`, a merge.

### Secrets for signing the APK

The release workflow **stops with an error** when they are missing. Otherwise
it would ship an APK signed with the debug key, because that is the fallback
path in `build.gradle.kts`. Four secrets in *Settings, Secrets and variables,
Actions*:

| Secret | Value |
|---|---|
| `ANDROID_KEYSTORE_BASE64` | the keystore encoded as base64 (command below) |
| `ANDROID_KEYSTORE_PASSWORD` | `storePassword` from `app/android/key.properties` |
| `ANDROID_KEY_ALIAS` | `chatt` |
| `ANDROID_KEY_PASSWORD` | `keyPassword` from `key.properties` (the same password here) |

The keystore as base64 (PowerShell, the result lands in the clipboard):

```powershell
[Convert]::ToBase64String([IO.File]::ReadAllBytes("$env:USERPROFILE\keys\chatt-release.jks")) | Set-Clipboard
```

The passwords are in `app/android/key.properties`, a file in `.gitignore`, so
it is neither in the repository nor in its history.

After every build the workflow runs `apksigner verify --print-certs` and wipes
the key off the machine, including when the build failed.

### Requiring tests before a merge

The workflows do not block a merge by themselves; that has to be turned on in
the repository settings: *Settings, Branches, Add branch ruleset* for `master`,
with **Require status checks to pass** and the `analyze i flutter test` check.
The same is worth adding for `develop`.

### The Flutter version in CI

Both workflows pin version `3.47.2`, the same one the project uses locally. An
accidental Flutter update has no way to break the build. When the SDK is
bumped, it has to change in both files under `.github/workflows/`.

## Releasing a version: the steps

CI takes care of the build and the tag; the rest is on your side:

1. Raise the number on the `develop` branch: `cd app && python tool/wersja.py
   0.5.0`.
2. Refresh the documentation screenshots if the UI changed:
   `flutter test tool/product_shots.dart` (needs a running emulator).
3. Open a PR from `develop` to `master` and wait for the tests to go green.
4. Merge the PR. The release workflow builds a signed APK, the portable Windows
   version (zip) and the installer (exe), creates the `v<version>` tag and
   publishes a Release with those three files.
5. Download the APK from the Release, install it on a phone and walk the
   [short checklist](#post-release-checklist).

The build commands above stay for local work and for checking something before
pushing to GitHub.

### Post-release checklist

Things no automated test can check, because they need two real devices on one
network:

- [ ] a scan finds the other device in both directions;
- [ ] a message arrives in both directions and gets a double check;
- [ ] a file of a few megabytes arrives after acceptance and the checksum
      matches;
- [ ] pairing: the codes on both screens are the same, and after agreeing the
      shield is green;
- [ ] a phone with the app closed and the screen off still receives;
- [ ] the Windows installer walks the whole road: install, Start menu shortcut,
      run, uninstall (the conversation history has to survive);
- [ ] after restarting the app the conversations and settings are in place.
